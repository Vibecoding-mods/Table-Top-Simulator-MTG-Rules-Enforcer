# Shrink the graph Unity marks every pass

The quarter-second freezes on this table come from Unity's `Resources.UnloadUnusedAssets` pass. It is a stop-the-world mark-and-sweep, and on this PC **MarkObjects is about 95% of every pass**. Its cost grows with the live object graph and the managed (Mono/MoonSharp) references inside it. It does not depend on how much the pass actually frees: passes that unloaded **0–2 assets still took 130–290 ms**. In the local logs the menu sits at about 60.9k Unity objects and a pass costs about 29 ms. The bare table pushes that to 69.9k objects, and the current game state to about 85.9k objects, where passes cost about 140–155 ms on a good session and 265–285 ms on a bad one. So the extra cost is what the table and its scripts add, not the engine. On the session-2 curve, reaching **≤120 ms means keeping the loaded-object count at or below roughly 80k** (no more than about 10k Unity objects of game content above the bare table) while cutting script and reference load. **50 ms would need about 65.5k**, below today's bare table, so the low end of the 50–120 ms target is only reachable if the table itself gets lighter, not just the game content. TTS gives Lua no call to trigger or suppress these passes. The levers are fewer live objects and managed references (strip dead weight, keep zones as deck data, aggregate tokens, reconcile instead of respawning, use shared textures, keep Lua state small), plus doing destructive work at moments where a hitch doesn't matter. Each lever can be checked against the "Loaded Objects now" and "MarkObjects" lines in Player.log.

## Freeing nothing still costs the full 130–290 ms pass

The pass marks every native Unity object reachable from the scene hierarchy, "including script components", along with static variables ([Unity 6.3: UnloadUnusedAssets](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Resources.UnloadUnusedAssets.html)). Then it destroys whatever stayed unmarked. A Memory Profiler developer explains on Unity's forum that the mark step also runs the scripting GC. Its time "scales linearly with the amount of Managed (aka Scripting) Objects", plus native objects, the managed shells around them, and the connections between all of them ([Unity Discussions](https://discussions.unity.com/t/how-to-avoid-gc-markdependencies/589376)). In the same thread, one log spent 81.4 of 82.2 ms in MarkObjects with only 2,246 loaded objects. Raw object count does not set the price; the managed graph does. Unity's own manual warns that UnloadUnusedAssets or GC.Collect "might take several seconds" in large projects ([Unity 6 manual](https://docs.unity3d.com/6000.0/Documentation/Manual/performance-managed-memory-introduction.html)). Incremental GC, which TTS credited with fewer stutters in v12 ([v12.0 notes](https://tabletopsimulator.com/news/patch-notes/update-v12-0-0)), only spreads routine collections across frames. It "doesn't speed up collection" ([Unity 6.3 incremental GC](https://docs.unity3d.com/6000.3/Documentation/Manual/performance-incremental-garbage-collection.html)), and the asset-unload pass still runs as one blocking operation.

The two local logs (Unity 6000.3.10f1, D3D11, RTX 4060) contain 30 passes. The other phases are flat: FindLiveObjects takes 5–9 ms, CreateObjectMapping 1–2 ms and DeleteObjects under 3 ms. All of the variance is in MarkObjects ([Player.log](%USERPROFILE%/AppData/LocalLow/Berserk Games/Tabletop Simulator/Player.log), [Player-prev.log](%USERPROFILE%/AppData/LocalLow/Berserk Games/Tabletop Simulator/Player-prev.log)).

| State | Loaded objects | Pass total | Cost per 1k objects |
|---|---|---|---|
| Main menu | 60,353–60,873 | 18–29 ms | 0.3–0.5 ms |
| Bare table, right after load | 69,857 | 211–214 ms | ~3.0 ms |
| Game state, session 2 steady | 84,722–85,921 | **131–159 ms** (two spikes at 281 and 293 ms) | ~1.6–1.8 ms |
| Game state, session 1 | 84,939 | **265–272 ms** | ~3.1–3.2 ms |

Three conclusions follow from this table. First, a table-added object costs **10–40 times more to mark than an engine baseline object**: about 4.6 ms per 1k objects above the menu in session 2 and about 10 ms per 1k in session 1, against 0.3–0.5 ms per 1k for the menu. That fits the forum explanation that cost follows managed references, and the table brings 69 scripted objects with about 652k characters of object Lua plus a Global script of about 190–200k characters. Second, the same object count gives passes **about 2x apart** depending on the session, and the extra variance most likely comes from managed-heap state (heap size after a burst of JSON parsing, imports or saves), which a non-compacting Boehm-style heap rarely gives back ([Unity 5.6 manual, older](https://docs.unity3d.com/ru/560/Manual/BestPracticeUnderstandingPerformanceInUnity4-1.html)). This is an inference, and the regime switch itself is unexplained. Third, how often the pass runs matters as much as how long it takes. Session 2 had 23 passes in about 76 minutes, roughly one every 3.3 minutes. The object count often did not change between passes, so they are not scene loads. TTS is evidently calling the method itself during play, and nothing published says when. One correction to the earlier report: the 401.7 ms figure in session 1 is the `UnloadTime` of the shutdown teardown, not a gameplay pass.

## A budget: 80k objects, 150 loose permanents, 450 textures

The save files explain where the objects come from. The "ENGINE MODE" table has **121 top-level objects, none of them contained, 69 scripted, 25 unique asset URLs**, and loads to about 69.9k Unity objects, which works out to about 79 Unity objects per table object once UI, bundles and buttons are included. The current autosave adds only 26 top-level objects (23 loose cards and 3 decks holding 279 cards) and about 97 new URLs, yet the logs put it about 16k Unity objects higher ([ENGINE MODE save](Documents/My Games/Tabletop Simulator/Saves/MTG 4 player table - ENGINE MODE.json), [TS_AutoSave_3.json](Documents/My Games/Tabletop Simulator/Saves/TS_AutoSave_3.json)). Visible content explains only about 3.6k of that, even at generous per-object estimates. The likely rest is leftovers from deck imports, opened importer and module UI, and the six serialized asset-bundle files that load at pass 4. This attribution is unverified, and it is the most important number to pin down.

A 4-player Commander game scales this up. The table below is an estimate built on assumed per-object costs, because no public source gives a Unity-objects-per-TTS-card figure.

| Item | Count | Unity objects each (assumed) | Subtotal |
|---|---|---|---|
| Loose battlefield cards | 100–240 | 30–80 | 3k–19k |
| Hand cards (live in hand zones) | ~28 | 30–80 | 0.8k–2.2k |
| Tokens | 20–50 | 30–80 | 0.6k–4k |
| Zone decks (library, graveyard, exile, command) | ~16 | ~50 | ~0.8k |
| Unique face textures | ~400–450 | 2–5 | 0.8k–2.3k |
| **Game total over the bare table** | | | **~6k–28k** |

On the session-2 fit (T ≈ 29 + 4.6 ms per 1k objects above 60.9k), that puts a full game at about **100 ms at 76k objects, 140 ms at 85k and 200 ms at 98k**, and about 180, 270 and 400 ms on the session-1 slope. That band covers both the 265–400 ms the user has observed and the 120 ms target. The concrete budget that lands under about 120 ms is this. The total stays **at or below about 80k loaded objects**. Game content stays **at or below about 10k objects over the bare table**. That means **at or below about 150 loose cards plus tokens across all four players**, with every library, graveyard and exile kept as a deck. Unique textures stay **at or below about 450**, with one shared back. The hidden-module script load gets **cut by about half**. To get toward 50–80 ms, the bare table itself has to come down from 69.9k objects and its managed load has to shrink, because 50 ms is about 65.5k objects on the good curve. Even if the budget is met, the unexplained bad regime can still produce an occasional 200 ms pass, so treat the budget as necessary rather than sufficient.

## Containers are data, and nothing else frees the scene

The most useful documented fact is this: "If an Object is placed inside of a bag/deck/etc, it stops existing and is no longer in the scene until it is pulled back out" ([TTS API intro](https://api.tabletopsimulator.com/intro/)). A container's `getObjects()` returns data sub-tables, not object references ([TTS API: Object](https://api.tabletopsimulator.com/object/)). A 60-card graveyard kept as a deck is therefore one scene object instead of 60, each with its own collider, rigidbody, renderer and TTS MonoBehaviours. SCED, the largest public card mod, keeps its library in an "AllCardsBag" and spawns cards from data on demand ([SCED releases](https://github.com/Chr1Z93/SCED/releases)). Hiding does not get you this. `setInvisibleTo` hides an object "as if it were in a hidden zone" ([TTS API: Object](https://api.tabletopsimulator.com/object/)), so the object stays live and is still marked on every pass. Moving it under the table or scaling it to zero leaves the same live object. One user observes that "the more objects in hidden zones that players can't see, the more it slows down the game" ([Steam](https://steamcommunity.com/app/286160/discussions/0/1457328392116386677)). Bagging works. Hiding doesn't.

Spawning can't be made free either. `reload()` "causes the Object to be deleted and respawned instantly", and `setCustomObject` only shows its changes after a reload. Swapping a live card's image is therefore a destroy plus a spawn, so a pool of blank cards that get re-skinned saves nothing ([TTS API: Object](https://api.tabletopsimulator.com/object/)). `setState` most likely works the same way; whether it keeps the GUID has not been checked. Decks have their own trap: they "only exist whilst they have more than one object contained". Taking the second-to-last card out destroys the deck and spawns the last card loose ([TTS API: Object](https://api.tabletopsimulator.com/object/)). Even so, deck operations beat loose cards. `spawnObjectData` is documented as "less resource intensive" than `spawnObjectJSON` ([TTS API: Base](https://api.tabletopsimulator.com/base/)), so building a mill target or a wiped board as **one deck from data** costs a single spawn instead of N. Sheets matter for textures. A sheet "can be loaded in as one texture which is applied to all of the cards" ([Steam](https://steamcommunity.com/app/286160/discussions/0/1473095331499866868)), and a TTS developer confirms that a loaded sheet is not loaded again for other decks. The same developer warns that sheets above 4096×4096 are bad practice and that a 12,800×6,720 sheet crashed the client ([Steam, developer "ulia"](https://steamcommunity.com/app/286160/discussions/0/1697169163408389253)). A 10×7 sheet at 4096 px gives about 409×585 px per card.

## Ranked techniques for the table's Lua, each with its check

The ranking weighs the likely cut in MarkObjects time against how strong the evidence is. Every check uses the same probe: the "Loaded Objects now" and "MarkObjects" values on the next `Unloading … unused Assets` line in Player.log, read from `Player-prev.log` after quitting, because the live log read 0 bytes while TTS was running. Compare those values in the same session at the same point in the game, because the 2x regime swing between sessions would otherwise drown the effect.

| Rank | Technique | What to do in this table | How to verify |
|---|---|---|---|
| 1 | **Attribute the 16k objects first** | Load the bare table, wait for a pass, then add one thing at a time: import one deck, spawn 50 loose cards, open the importer UI, start the game. Note wall-clock time for each step. Lua `print` markers may also reach the log, but check that they do. | The delta in "Loaded Objects now" per step gives a real objects-per-card figure, which replaces the 30–80 assumption, and shows which step owns the 16k |
| 2 | **Strip dead weight from the bare table** | Delete the hidden 99-card DeckCustom (81 unique face URLs) and the loose "Exdeath" card at Y −13.5/−14. Review the 6 asset bundles at Y −46.1 (3 URLs, 4 of them sharing one) and the PiecePack at Y −100. Keep one importer instead of two rikrassen copies (34k chars each) plus the 140k-char Card Importer. Park idle modules (Morphin' Time, Pirate Cannon, Phasing, etc.) in a saved-object bag, where they become inert data. | The bare-table steady-state pass drops below 69.9k objects. "Serialized files now loaded" falls from 6 if bundles are removed. The total Lua chars in the save drops. |
| 3 | **Zones as decks; mills and wipes as one deck spawn** | Library, graveyard, exile and command stay decks. For a mass mill, take the cards' data, append to the target deck's `ContainedObjects`/`CustomDeck` and use a single `spawnObjectData` (or `putObject` into the live deck) instead of laying cards out. For a board wipe, move each permanent into the graveyard deck and do not respawn anything. Avoid passes through a 1-card deck. | Mill 20 cards: the object count should rise by about 0, not by 20 × (objects per card). The pass after a wipe should come in *below* the one before it. |
| 4 | **Reconcile, never rebuild** | Key live objects by engine card id (in `memo` or GM notes). On each engine update, move or rotate the objects that exist, spawn only new ids and destroy only removed ids. Tapping is `setRotation`. Counters use `setName`, decals or XML labels. Never use `destruct`+respawn or `setCustomObject`+`reload` for a state change. Put both faces of a double-faced card on the face and back so it can `flip()`. Pool only fixed-look objects such as dice and counters. | Count spawns per turn in a Lua counter, which should be close to the number of new cards. The object count should stay flat across 10 turns with no new permanents. |
| 5 | **Aggregate tokens** | Show one token per (type, controller, tapped, modified) group with a count label such as "Soldier x12". Split one out only when it diverges. Use one stable URL or one token sheet for common tokens. | Make 20 tokens: the object delta should be about 1 group object instead of 20 objects. |
| 6 | **Share textures** | Use one byte-identical back URL. Use identical URLs for every copy, query strings included. Build sheets for each player's known 100-card deck outside TTS and emit CustomDeck entries with width and height above 1 (at most 4096 px, no duplicate or empty slots). Use Scryfall "normal" (488×680) rather than large or png. | The unique-URL count in the save drops from about 450 toward 10–20 per player. The pass after deck load has fewer objects. |
| 7 | **Shrink the managed graph** | Keep card data compact. Drop large cached JSON strings. Move per-object scripts into the Global script, which operates on GUIDs. Cut the 321 `createButton` sites and 102 `Wait.time` timers. Use targeted UI updates instead of rebuilds. | At the same object count, MarkObjects should fall: compare the pass time per 1k objects before and after. |
| 8 | **Time the unavoidable** | Batch imports, resets and large spawn waves into setup and between games. Spread waves over frames with one coroutine (`coroutine.yield(0)` every 10–25 operations). Wrap bursts in `storeRewindState`/`allowRewindStore` (v14.0+) ([v14.0 notes](https://tabletopsimulator.com/news/patch-notes/v14-0-public-beta-engine-upgrade-unity-6-lts)). After deck import, and as the game reset, save and reload, which clears import leftovers and probably the inflated heap. | Fewer passes land in the middle of a turn. After a save-and-reload, a pass in the same game state should match the session-2 good regime of about 1.6 ms per 1k objects. |

Two cautions apply to the ranking. Techniques 3–6 cut *object count*. If the 2x regime comes from managed-heap state, techniques 7 and 8 are what close the remaining gap, and nothing in the evidence yet says which kind of fix dominates. Also, TTS v13.1 fixed a memory leak with custom assets and "greatly reduced the lock up when spawning lots of objects" ([v13.1 notes](https://tabletopsimulator.com/news/patch-notes/v13-1-native-file-browser-cloud-manager-and-rewind-time-improvements-optimizations-and-much-more)). Rapid create and destroy was a known engine weak spot, so churn probably costs more than its object delta shows. It plausibly creates the garbage that pushes a session into the bad regime.

## Conclusion

The shift in understanding is that this is a **managed-reference problem with an object-count proxy**, not an object-count problem. Engine objects cost about 0.4 ms per 1k to mark, while table objects cost 5–20 ms per 1k, so the cheapest gains are probably in what the bare table carries before any card is played: about 300k characters of hidden-module Lua, two duplicate importers, a stray 99-card deck and six bundles. The game-content budget can't reach the bottom of the target alone. The 50 ms end needs a lighter base table. A heavy board that stays under about 150 live cards and is reconciled rather than rebuilt should hold passes near 100–120 ms in the good regime.

Three unknowns limit any prediction to a 2x band. Nothing published says what triggers TTS's passes. Nobody has measured how many Unity objects a TTS card is. The good and bad regimes at identical object counts are unexplained. The attribution run in technique 1 resolves the second and narrows the first, and a save-and-reload comparison tests the heap hypothesis behind the third. Both runs fit in one evening and would turn this budget from an estimate into a measured one.
