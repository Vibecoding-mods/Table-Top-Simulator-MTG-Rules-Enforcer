# Fix the host before renting servers

The cheapest way to run this Commander setup on a strong, stable connection is to keep hosting Tabletop Simulator on the home PC and spend nothing. The friend's 10-second chop was almost certainly the host freezing, and that was fixed on 2026-10-19. Rewind snapshots were taking **2.7 s every ~10 s** because the engine's CustomDeck keys were huge, and each `destruct()` added **~360 ms**. With both fixed, a clean full game now has a worst host frame of about **244 ms**. TTS cannot be moved to a cheap server. It has **no dedicated or headless server**, so a cloud host means renting a whole Windows GPU desktop at **$0.65–0.73 per hour**. That works out to about $15–20 a month for four 4-hour game nights, about $50 for ~70 hours, and **$480–535 a month if left on**. Moving only the Node bridge and Forge to a Linux VPS is cheap: **about $1–5 a month** billed hourly for session time, or $8.50–48 a month always on. It adds only **30–120 ms** per engine round trip, but it does nothing for the TTS network path between players. Its real value is that any player with good upload could host. The ranking below is: fix and verify the home host for free, use a VPS only if a $0 test shows Forge hurts the host, and rent a cloud GPU host for game nights only if the host's home upload turns out to be the bottleneck.

## The 10-second chop was the host freezing, and it is fixed

TTS is host-authoritative. One player's game simulates the table and sends state to everyone else. Since v14.1/v14.2 (Feb–Mar 2026), that traffic is encrypted and **routed through Steam relays**, which made the old port-forwarding and proxy advice obsolete ([TTS v14.2 notes](https://tabletopsimulator.com/news/patch-notes/v14-2-public-beta-updated-steam-p2p-networking-and-engine)). TTS also stores a rewind snapshot of the whole table on a timer. Users report the console default `rewind_interval` is **10.0**. On large mods, FPS drops to about 1 "every 10 seconds on the dot", and setting the interval to 0 stops it ([Steam bug report](https://steamcommunity.com/app/286160/discussions/3/1744521646952260615/)). This project measured the same event on its own table. Snapshot cost grows with each card's CustomDeck number: key 1 costs 0 ms, 999,999 costs 2.5 ms and 12.5 million costs 25 ms per card. The engine's old hash keys therefore made **every snapshot take 2.7 s** ([local measurement, tts-perf-facts.md](local measurement notes (not published))). While the host's main thread is frozen it sends nothing, so a remote player sees the table stall and then jump. That is a 2.7-second hitch repeating every 10 seconds, exactly the chop the friend described. The engine now uses sequential keys starting at 3000 and disposes cards into a trash deck instead of calling `destruct()`.

Two caveats keep this from being certain. No official source confirms that only the host snapshots, or that a host freeze stalls client updates; both follow from the architecture. Second, a quick test settles it: if the friend still sees a 10-second chop alone in single-player, the cause is on their own machine. Old saved objects that still carry big keys keep snapshots slow until they are renumbered. The ~244 ms worst frame that remains matches the size of Unity's asset-unload passes measured earlier on this PC (130–290 ms, about every 3.3 minutes). That is a host CPU cost, and no hosting change touches it ([Unity: UnloadUnusedAssets](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Resources.UnloadUnusedAssets.html)).

## A cloud TTS host means renting a whole GPU desktop

There is no server binary to put on a VPS. Steam answers to "Dedicated server" say there are none, and "there's no official servers for anything TTS, it is all user created/run" ([Steam](https://steamcommunity.com/app/286160/discussions/0/1473095331499476124/), [Steam](https://steamcommunity.com/app/286160/discussions/0/4336483638879367884)). No `-batchmode` server command is documented ([tldr-pages #17125](https://github.com/tldr-pages/tldr/issues/17125)). No public report shows TTS hosted on AWS, Azure, GCP or a VPS, or running on a CPU-only machine. A cloud host is therefore the normal game client on a GPU VM, logged into a Steam account that owns TTS, set up over Parsec or RDP and left in the lobby. If that machine crashes or is reclaimed, the session ends, so spot instances are out. A weak GPU is enough: users run card tables on Intel integrated graphics ([Steam](https://steamcommunity.com/app/286160/discussions/0/4939856028572546858/)). An entry T4 or a fractional A10 is plenty.

Hourly GPU VMs with Windows cluster at about **$0.70 an hour**. AWS g4dn.xlarge (T4) is $0.526/h on Linux ([Vantage](https://instances.vantage.sh/aws/ec2/g4dn.xlarge)). The Windows rate is about $0.71/h, but that figure comes from a single unofficial calculator ([course calculator](https://michael-lange-s-school.teachable.com/courses/2525668/lectures/55395584)). Azure NV6ads A10 v5 is **$0.73/h on Windows, or $532.90/month** always on ([cloudprice.net](https://cloudprice.net/vm/Standard_NV6ads_A10_v5)). GCP n1-standard-4 plus a T4 at $0.35/GPU-hour, plus the Windows license, comes to about $0.72/h ([GCP GPU pricing](https://cloud.google.com/compute/gpus-pricing?hl=de), [gcloud-compute.com](https://gcloud-compute.com/n1-standard-4.html)). airgpu wraps AWS hardware in a gaming PC **from $0.65/h, with a $7/month 100 GB storage minimum** ([cloudbase.gg](https://cloudbase.gg/airgpu-cloud-gaming/), [airgpu](https://airgpu.com/shadow-pc-alternative/)). Shadow PC is a flat $29.99–59.99 a month, but it has **4–8 hour session caps, 120–210 hour monthly caps and a 30-minute idle shutdown** ([Shadow offers](https://shadow.tech/us/shadowpc/offers/)). A long Commander game can hit a 4-hour cap, and an unattended host may count as idle. Vultr's fractional A16 launched at $21.50/month in 2023, which would be the only affordable always-on option ([BusinessWire](https://www.businesswire.com/news/home/20230209005178/en)). Its current price, its Windows fee and whether it can run TTS are all unverified. Egress is small: TTS state sync is estimated at a few GB a month, inside AWS's 100 GB free tier ([egresscost.com](https://egresscost.com/aws/data-transfer-pricing)). Leaving a remote-desktop stream open all night would cost more than the game traffic.

What a cloud host buys is datacenter upload and independence from any one player's PC. Everyone, the organizer included, becomes an equal client over Steam relays. What it does not fix: the host still runs Unity's unload passes and snapshots, and every player still decodes card images locally. Running the Docker stack on the same Windows cloud VM is a further unknown. WSL2-based Docker needs nested virtualization, which these VM types may not offer, so the safer pairing is a cloud GPU host plus a separate Linux VPS for Forge.

## A $1–5 VPS frees host CPU but not the network

Forge is light on memory. The published manabrew-node is a GraalVM native image with an **1100 MB heap cap**, and it idles at **248 MiB RAM and 0.4% CPU**. The relay uses 24 MiB ([local Dockerfile](../manabrew/manabrew-rs/crates/self-hosted-node/Dockerfile), local `docker stats`). A 2 vCPU/4 GB box is enough for one table, and 4 vCPU/8 GB is comfortable. The image is **linux/amd64 only**. Oracle's free ARM tier would need a native arm64 rebuild. That tier is now 2 OCPU/12 GB, not the often-quoted 4/24, and it reclaims instances that sit idle for 7 days ([Oracle docs](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)), so it is free but fiddly.

US prices moved sharply in 2026. Hetzner's 15 June repricing took the US CPX31 (4 vCPU/8 GB) from $24.99 to **$73.49/month**, so Hetzner is no longer the default pick ([Hetzner docs](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)). The cheapest hourly-billed options are DigitalOcean Basic at **$24/month ($0.0357/h) for 2 vCPU/4 GB and $48/month ($0.0714/h) for 4/8**, billed per second ([DigitalOcean](https://www.digitalocean.com/pricing/droplets)). Linode's shared plans cost the same ($24 and $48), and its dedicated 4 vCPU/8 GB is $72 ([Akamai](https://www.akamai.com/cloud/pricing/cpu)). Prepaid budget hosts are cheaper again. OVHcloud VPS-2 (4 vCore/8 GB) starts at **$8.50/month**, which is probably a 12-month rate ([OVHcloud](https://us.ovhcloud.com/vps/)). Contabo Cloud VPS 4 is €5.50 including VAT on a 24-month term ([Contabo](https://contabo.com/en-us/vps/)). netcup's US 4-core/8 GB is $0.045/h, about $33 a month always on ([elest.io notice](https://docs.elest.io/books/announcement/page/netcup-price-change-notice-effective-april-1st)). Billed only for game time, a DigitalOcean 4/8 droplet costs **about $5 for 70 hours a month**, and a 2/4 droplet about $2.50. The catch is that a powered-off droplet still bills, so the server has to be destroyed and restored from a snapshot each time, with snapshot storage billed extra.

Latency cost is modest. Each prompt adds one internet round trip to a nearby region, an estimated 10–40 ms, plus TLS setup. That totals roughly 30–120 ms against Forge's 100–900 ms of thinking time. The return path matters more than the region. TTS receives the bridge's custom messages on localhost through the External Editor API, where `onExternalMessage` already arrives as a Lua table ([External Editor API](https://api.tabletopsimulator.com/externaleditorapi/)). The project measured this path as free. A VPS cannot reach the host's localhost, so the design should keep a tiny helper on the host PC. The helper holds an outbound WebSocket to the VPS and forwards into port 39999, which preserves the zero-cost path and opens no inbound port. The alternative is having Lua poll the VPS with `WebRequest`, which returns text that must be JSON-decoded in Lua. Large decodes have frozen TTS for seconds ([Nolt #931](https://tabletopsimulator.nolt.io/931)), so polling risks reintroducing the stutter the project just removed. On security, expose only 443 behind Caddy with a long header token, keep the relay port (9443) internal, and replace the default `tts-local` key, mirroring upstream's production compose file ([local compose.production.yml](../manabrew/compose.production.yml)).

The honest scorecard is narrow. Offloading removes Forge's AI bursts from the host's 6-core/6-thread Ryzen 5 3500, and it frees the WSL2/Docker VM's memory if Docker is stopped entirely. Smoother host frames mean smoother sync for everyone. It does not change the host's upload, the Steam relay path, peers' ping, unload passes, snapshots or image decoding. The 244 ms worst frame was recorded with Forge running locally, which suggests Forge is not today's limiting cost. Try a $0 test before paying: cap Forge at 2 cores with low priority and compare frame times in PresentMon. If nothing changes, a VPS buys no smoothness. Its remaining value is flexibility. With Forge off the PC, whichever friend has the best upload can host while running only the small helper.

## Host upload matters more than download, and stability more than speed

No official per-player bandwidth figure exists, so the guidance rests on community reports and our own measurement still to come. The consistent message is that **upload is what counts**. Players say "You need to check the upload speed, download speed doesn't really matter", and that TTS uses "considerably more network than other p2p games", growing with each connected player ([Steam](https://steamcommunity.com/app/286160/discussions/0/1327844097123386340)). A 5 Mbps host was saturated by a single table flip in 2015 ([Steam](https://steamcommunity.com/app/286160/discussions/0/618457398965740400)). A host advertising 10 Mbps had clients at 200+ ping because that was its download figure, not its upload ([Steam](https://steamcommunity.com/app/286160/discussions/0/215439774867842113/)). Netcode has since become leaner: v14.0 tightened bitpacking and v14.1.5 cut a packet per second per client ([patch notes](https://tabletopsimulator.com/news/patch-notes)). Card images do not load the host. Each client fetches them from their URLs and caches them ([TTS KB](https://kb.tabletopsimulator.com/getting-started/troubleshooting/)), so a player's slow first card load reflects their own download and the image server. Steadiness matters as much as speed. Small state updates must arrive evenly, and congested uplinks add huge delay: FCC data shows DSL upstream latency averaging **656 ms under load** ([FCC MBA](https://www.fcc.gov/reports-research/reports/measuring-broadband-america/measuring-fixed-broadband-eleventh-report)). Wi-Fi and bufferbloat turn smooth updates into bursts that look like rubber-banding.

Chops seen by clients therefore fall into three groups. The first is host stalls: the old 2.7 s snapshots, `destruct()` pauses, remaining unload passes, and table flips or mass physics. The second is the network: host upload saturation, packet loss, Wi-Fi, and VPNs or Hamachi adding a hop ([Steam](https://steamcommunity.com/app/286160/discussions/0/1327844097123386340)). The third is the client's own PC: first-time image decoding and its own Unity passes. Delayed button clicks have a specific cause. Lua runs on the host, so a remote click on an XML button travels to the host, runs `onClick(player, value, id)`, and comes back as replicated `setAttribute` changes ([TTS API: UI](https://api.tabletopsimulator.com/ui/), [Input Elements](https://api.tabletopsimulator.com/ui/inputelements/)). A healthy click should therefore take roughly a relay round trip plus a host frame, estimated at 100–250 ms. Multi-second delays mean the host stalled. Before the fix, a click landing in a snapshot waited up to 2.7 s, and `destruct()` in the click path added 360 ms per card. Instant local `pressedColor` feedback, cheap handlers and a queue against double clicks hide the remaining round trip.

A notice for players, labeled as a guideline rather than a TTS specification, could read:

> **Hosting:** the host needs at least **5 Mbps of steady upload** (10 Mbps or more recommended) on a **wired** connection, with no VPN and nobody else uploading or streaming on that line during the game. Run an upload test (not download) before offering to host. **Joining:** any stable broadband works. Wired or strong Wi-Fi is preferred, and VPNs should be off. Your first game loads every card image, so join a few minutes early and let it finish. If you see a stall every 10 seconds even when playing alone, tell the host, because that points to your own PC.

Back the number with a measurement: watch the TTS process's send rate in Windows Resource Monitor on the host with three players connected, idle and then during a big board change.

## Conclusion

The question changed once the freeze was measured. "Rent a better connection" was the obvious answer to a remote friend's lag, but the chop was a 2.7-second host stall that no datacenter would have removed. A cloud host running the old engine would have chopped exactly the same way, at $0.70 an hour. Lag in this setup comes mainly from host frame stalls; bandwidth is secondary. Money should follow measurement in two cheap steps. First, confirm with the friend that the chop is gone and record the host's real upload use. Second, run the Forge-throttle test. Only a measured upload ceiling justifies the ~$15–50 a month for game-night GPU hosting, and only a measured Forge effect justifies the $2.50–5 VPS.

The VPS route is undervalued as a lag fix but useful for a different reason. Once Forge and the bridge run off any one PC, hosting is no longer tied to the person who owns Docker. Whoever has the best upload that night can host, which is the community's oldest piece of advice for TTS lag. The risk to manage is the return path. Keep the free External Editor path through a small local helper rather than polling over `WebRequest`, or the move will trade a CPU problem for a JSON-decode stall.
