# Hunt the stall that grows with time

Tabletop Simulator's stutter in a heavily scripted card mod usually comes from **periodic, whole-scene main-thread stalls whose cost grows with how much is loaded and how long the session has run**, not from any single scripted operation. That is why each piece measures cheap in isolation and the game still hitches in real play. The strongest lead is on this PC: the previous session's Unity log shows repeated `Unloading N unused Assets` passes. Each one froze the main thread for **about 265–285 ms**, one took 401.7 ms, and their cost rose with the loaded-object count (18 ms at about 60k Unity objects, about 270 ms at 82–85k). The other likely causes are rewind and autosave snapshots of the whole table, bursts of first-time card images being decoded and DXT-compressed, Mono garbage collection fed by MoonSharp allocations, and an uncapped frame rate competing with the WSL2/Docker rules engine for a 6-core, 6-thread CPU. Mod authors fix this by stopping spawn/destroy churn (keep a pool of card objects and move them), spreading engine-driven work across frames with one coroutine queue, sending diffs instead of full board state, suppressing rewind stores during scripted bursts with the v14 Lua API, pre-warming the image cache, and keeping `onSave`, `onUpdate` and `print` close to zero cost. The first step is diagnostic: put Player.log unload lines, a PresentMon frame-time capture and WSL CPU usage on one timeline to see which of these causes your stutters.

## Isolated benchmarks miss what scales with scene size

Your benchmarks measure the cost of an operation. The likely culprits instead cost something proportional to the *whole scene*, and they fire on timers or engine triggers that a short micro-benchmark never hits. Unity's `Resources.UnloadUnusedAssets` decides what is unused by "walking the whole game object hierarchy", static variables included ([Unity docs](https://docs.unity3d.com/ScriptReference/Resources.UnloadUnusedAssets.html)). Developers of other Unity games treat each call as a frame hitch and schedule it only at quiet moments ([Unity docs](https://docs.unity3d.com/410/Documentation/ScriptReference/Resources.UnloadUnusedAssets.html), [Adventure Creator forum](https://www.adventurecreator.org/forum/discussion/comment/52394)). On this machine, `AppData\LocalLow\Berserk Games\Tabletop Simulator\Player-prev.log` records these passes at **"Total: 284.5 ms ... MarkObjects: 276.4 ms"**. Almost all of that time is the mark phase, which scales with the number of live objects. A quarter-second freeze at irregular moments is a close match for "random stutter". This evidence comes from local inspection, so there is no public URL. Which TTS actions trigger the passes is undocumented. Object destruction, save loads and rewinds are the plausible candidates, and no source confirms whether TTS calls the method directly.

Rewind is the second scene-wide cost. A 2018 explanation describes rewind as a JSON snapshot of the whole table written **about every 10 s**, with about 30 kept ([Steam](https://steamcommunity.com/app/286160/discussions/0/350544117177313040)). Autosave defaults to **every 5 minutes** ([Steam](https://steamcommunity.com/app/286160/discussions/0/2534848209921991774)). Users report 4–8 s host-side freezes that they attribute to snapshotting and describe as "not network related" ([Nolt #2215](https://tabletopsimulator.nolt.io/2215)). Berserk's own v14.0 notes confirm that "rewind states are stored periodically" and warn that a store "in the middle of a complex scripted change" can capture an inconsistent state ([v14.0 notes](https://tabletopsimulator.com/news/patch-notes/v14-0-public-beta-engine-upgrade-unity-6-lts-copy)). Every autosave also calls each object's `onSave()`. SCED (the Arkham Horror LCG mod) removed `onSave` from its counters for exactly that reason ([SCED PR #920](https://github.com/Chr1Z93/SCED/pull/920)). One caution: an October 2024 thread reports freezes every 3 minutes *with autosave and rewind both off*. One poster cured it by upgrading from 16 to 32 GB RAM and another did not ([Steam](https://steamcommunity.com/app/286160/discussions/0/4700160645248205392)), so snapshots do not explain every periodic freeze.

The third interaction is CPU contention. `Graphics.json` on this PC has **VSync false, CapFPS false, CustomCapFPSRate 0**: TTS renders uncapped and uses every cycle it can get. By default WSL2 may schedule on all logical processors and claim 50% of host RAM ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)). On a 6-core CPU without hyper-threading, a burst of rules-engine work can preempt TTS's main thread at the moment it is also processing the resulting card updates. Neither side looks expensive measured alone, which fits your results exactly. This is an inference with no TTS-specific measurement behind it, but testing it is cheap.

## Card images cost most the first time they load

TTS keeps two caches. `Mods/Images` holds the downloaded originals. `Mods/Images Raw` holds GPU-ready `.rawt` textures that are already block-compressed and mipmapped. On this PC the **2,834 img.klrmngr.com cards average 108 KB as webp but 551 KB as `.rawt`**. Each `.rawt` header records a Unity texture format, and the file sizes match the format exactly. Format 10 is DXT1: 672×936 at half a byte per pixel, plus a mip chain, is exactly 420,064 B. Format 12 is DXT5, at 839,896 B. All of this comes from local inspection of the cache. So a card's first appearance costs a download, a webp decode, mip generation and DXT compression on the client. Later appearances read the `.rawt` and upload it. Caching saves bandwidth but cached files "still need to be loaded" ([Steam](https://steamcommunity.com/app/286160/discussions/0/4658391921147555656)). Generic Unity image loading can block the main thread for "a hundred milliseconds" up to "a few seconds" on large images, and DXT compression inside `LoadImage` runs synchronously ([UnityAsyncImageLoader](https://github.com/aMidnightNova/UnityAsyncImageLoader), [Unity LoadImage docs](https://docs.unity3d.com/2017.4/Documentation/ScriptReference/ImageConversion.LoadImage.html)). No source says which thread TTS uses for this work. The community "Mod Threading" toggle suggests at least part of it runs on worker threads ([SCED FAQ](https://steamcommunity.com/workshop/filedetails/discussion/2495129405/2952663522489531774)).

Two findings matter for this table. First, v14.0 (Unity 6 LTS) added WebP support, made "loading new (uncached) images ... more performant", and reduced crashes "when large or many new images are being loaded" ([v14.0 notes](https://tabletopsimulator.com/news/patch-notes/v14-0-public-beta-engine-upgrade-unity-6-lts-copy)). That is an official admission that bursts of new images were a known stress case. Many uncached cards resolving together, for example when an opponent's new deck hits the table, is the realistic burst. Second, **886 of the 2,834 klrmngr cards (31%) were stored as DXT5 with a transparency flag**. If the server emits an alpha channel, for example for rounded corners, those cards cost twice the VRAM and disk and take a slower encode. Serving opaque webp would halve that. One image per card also means one texture, and very probably one material, per unique card: about 200 textures, no batching across faces, and 200 separate load events where a 10×7 sheet would need one. Total memory is not the issue, since 200 opaque DXT1 cards come to about 84 MB of VRAM. The issue is the number of separate load events and assets, and the asset count is exactly what makes unload passes longer.

Spawning adds to this. The official API says "Objects take a moment to spawn" and recommends `spawnObjectData` as "less resource intensive" than `spawnObjectJSON`. `setCustomObject` only takes effect after `reload()`, which "causes the Object to be deleted and respawned instantly" ([API base](https://api.tabletopsimulator.com/base/), [API object](https://api.tabletopsimulator.com/object/)). Changing a card's face on an existing object is therefore a full despawn and respawn, not a texture swap. A redraw model that destroys and respawns cards each time the engine sends state produces asset churn, which feeds both the unload passes and snapshot size.

## MoonSharp makes Lua garbage into Unity garbage

MoonSharp chose this trade-off on purpose: its goal is "to sacrifice Lua raw execution speed in order to gain performance on Lua/C# cross calls", and it "relies on .NET/Mono standard GC" ([MoonSharp](https://www.moonsharp.org/moonluadifferences.html)). Every Lua table, closure, concatenated string and boxed value is a managed heap object, collected by the same GC that runs the game. Unity's GC runs when an allocation doesn't fit and causes noticeable pauses when collections are frequent or large ([Unity Manual](https://docs.unity3d.com/cn/2022.3/Manual/performance-garbage-collector.html)). The only profiled case linking MoonSharp to periodic stutter is from Kerbal Space Program, not TTS. There, 124 Lua-evaluated variables produced 30–40 MB of allocations per profiler sample and **cost 1.47 ms versus 0.23 ms for 318 native delegates**, and users saw periodic frame stutters the developer blamed on interpreter garbage ([AvionicsSystems #5](https://github.com/MOARdV/AvionicsSystems/issues/5)). An old benchmark puts MoonSharp at roughly 10x slower than native Lua on pure-Lua work ([MoonSharp group](https://groups.google.com/g/moonsharp/c/oXM5vZFNbPY)). That figure is order-of-magnitude and dated. GC pauses also come late: the garbage from a redraw is often collected several frames afterwards, so the hitch shows up after the work that caused it, and a profile of the redraw alone looks clean.

JSON is the best-documented Lua-side freeze source. An 80 KB payload took a little over 4 s with `JSON.decode` and about half that with MoonSharp's `json.parse`, and both froze the UI ([Nolt #931](https://tabletopsimulator.nolt.io/931)). Large Scryfall responses froze TTS for about 4 s ([Nolt #968](https://tabletopsimulator.nolt.io/968)). In 2024 SCED cut a 4 s load lock to about 2 s by switching to `json.parse`, calling `getData()` once instead of inside the loop condition, and yielding every 20 cards instead of every 10 ([SCED PR #630](https://github.com/Chr1Z93/SCED/pull/630)). These timings predate v14, and v14.0 and v14.2 both shipped JSON fixes ([patch notes](https://tabletopsimulator.com/news/patch-notes)), so re-measure them on your build. `onExternalMessage` already receives a Lua table ([External Editor API](https://api.tabletopsimulator.com/externaleditorapi/)), so a JSON string nested inside the message means parsing it twice.

The External Editor API has costs of its own. TTS forwards every `print()` (message ID 2) and every error (ID 3) to port 39998 ([External Editor API](https://api.tabletopsimulator.com/externaleditorapi/)). The reference VSCode adapter handles one message per TCP connection ([TTSAdapter.ts](https://github.com/rolandostar/tabletopsimulator-lua-vscode/blob/master/src/TTSAdapter.ts)). A debug print inside a 200-card loop therefore costs a string build, a chat-UI append, JSON serialisation and a localhost connection, 200 times over. Whether TTS's send path blocks the main thread is unconfirmed, because the assembly was not decompiled. `sendExternalMessage` during `onLoad` has been reported to drop, duplicate and reorder messages ([Nolt #2215](https://tabletopsimulator.nolt.io/2215)). On the scheduling side, 200 `Wait.frames` closures per redraw means 200 allocations and 200 scheduler entries. `Wait.condition` without a timeout polls forever. `onUpdate` runs every frame on every object that defines it ([API Wait](https://api.tabletopsimulator.com/wait/)). The Wait class was optimised in v14.0.3, and `Wait.collect` was added for joining many async results ([patch notes](https://tabletopsimulator.com/news/patch-notes)).

Physics and UI matter less but are easy to fix. Locked objects are "frozen in place (preventing physics interactions)". `setPositionSmooth` takes a `collide` flag. Collision "stay" events "may negatively impact performance" ([API object](https://api.tabletopsimulator.com/object/)). v14.0 added a minimal-collider toggle for cards ([v14.0 notes](https://tabletopsimulator.com/news/patch-notes/v14-0-public-beta-engine-upgrade-unity-6-lts-copy)). In the XML UI, `setXml` is an asynchronous full rebuild and `show`/`hide` play animations, unlike the `active` attribute ([API UI](https://api.tabletopsimulator.com/ui/)). Prefer targeted `setAttributes` on stable IDs. No source has measured the cost of `highlightOn`, context menus or `setName`. Writing them only when they change is cheap insurance.

## Recommendations ranked by likely impact

The ranking weighs how much each fix is likely to cut the observed symptom (irregular quarter-second to multi-second freezes in long real games) against how strong the evidence is. Items 1–4 target scene-wide stalls and contention. Items 5–8 reduce how much each burst costs.

Lowering graphics quality will not help: Shadows, SSAO and MSAA are already off and the GPU is an RTX 4060.

### What each stutter signature points to

PresentMon's columns separate the causes. On a CPU or main-thread hitch, **MsCPUBusy spikes while MsGPUBusy stays small** ([PresentMon](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)). That is the expected case here. Within that case, timing tells the causes apart. A spike that matches a Player.log unload line and tracks object count means asset unload. Spikes at fixed intervals (about 10 s or about 5 min) mean rewind or autosave. Spikes when an opponent's new cards first appear mean image decode. Spikes that coincide with `vmmem` CPU bursts mean scheduler starvation. Spikes alongside hard-fault surges in Resource Monitor mean paging. One practical note: the live Player.log read 0 bytes while TTS was running, so read `Player-prev.log` after quitting. The Unity Profiler cannot attach to retail TTS. Windows Performance Recorder (`wpr -start GeneralProfile -start CPU`) can assign stalls to threads, but no TTS-specific guide for it was found.

## Conclusion

Your result, that each part is cheap alone but the game stutters in real play, is evidence for a cause that scales with session state rather than a contradiction. TTS's worst stalls (asset-unload marking, rewind snapshots, autosave with `onSave`, and GC) each cost in proportion to everything the table holds, and they fire on schedules that no single-operation benchmark triggers. The design consequence is that, past a modest per-frame budget, how fast the redraw runs matters less than how many objects, textures and garbage the redraw leaves behind. A pooled, diff-driven table with a stable object count should stutter less in turn 15 than a respawning table does in turn 1, even if each redraw takes the same time. The local measurement of unload cost rising from 18 ms to about 270 ms as loaded objects grew suggests exactly this.

Three questions remain open and should be settled by measurement rather than more reading. What triggers TTS's unload passes? Does `sendExternalMessage` or print forwarding block the main thread? How much do v14.2's MoonSharp and JSON updates change the old 2x–100x `JSON.decode` versus `json.parse` gap? Decompiling `Assembly-CSharp.dll` would answer the second question directly. A log-plus-PresentMon capture from one real game would likely rank the rest within an afternoon.
