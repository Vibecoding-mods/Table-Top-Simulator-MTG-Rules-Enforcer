# FX research: what we have, what the table knows, and how to build the four new effects

Research only, 2026-11-12. Nothing was edited apart from this file. The four effects asked for:

1. **Death**: a permanent goes to the graveyard.
2. **Board wipe**: coloured by the spell that caused it.
3. **Exile**.
4. **Damage bolt**: a projectile from the damage source to the creature or player hit.

So **a new effect is a few lines of C# and one batch build**, with no editor clicking.

### 1.3 How TTS exposes it, and how the table uses it (`tools/engine-renderer.lua`)

- Lua API: `obj.AssetBundle`, with these calls:
  - `getTriggerEffects()`: a list of `{index, name}`;
  - `playTriggerEffect(index)`;
  - `getLoopingEffects()`, `playLoopingEffect(index)`, `getLoopingEffectIndex()`.
- **No parameters**: no colour, size, speed or target. Index is from 0. The table maps name → index once (`FX.rigIndex`) and looks effects up **by name**, so the order in the bundle doesn't matter.
- **Rigs** (`FX.findRigs`, `FX.addRig`, `FX.rigPlay`, at 1944-2082):
  - 6 copies (`FX.RIGS`) of the bundle object, GM notes `engine:fx`, locked, `interactable = false`, parked at y −30 (x −40…−31, z 30).
  - They are spawned **once** by `spawnObjectData` (`Custom_Assetbundle`) when the save has none and `engineFxBundle.fx` is set. After that they stay in the save and are never destroyed. The spawn data needs a `Transform`, or real TTS raises.
  - Only when there are zero rigs: the code doesn't top up a save holding fewer than `FX.RIGS`.
- **One effect** (`FX.rigPlay`):
  - picks a free rig (`busy` until the effect's length + `RIG_TAIL` 0.6 s);
  - `setInvisibleTo(players with effects off)`, but only when that set changed;
  - `setRotation(0, seatRotY, 0)`, but only when the seat changed;
  - `setPosition(spot + 0.3 y)` at once;
  - `playTriggerEffect` at least `RIG_LEAD` 0.1 s later, so clients have the new position first;
  - `setPosition(home)` after the effect is over.
  - With no rig free, or no such effect name, it falls back to the Object UI slot, which needs no bundle.
- **Name map**:
  - `FX.RIG_NAME`: death→`death`, wipe→`death_wipe`, exile→`exile`, countered, damage, player→`player_hit`, counter, counter_minus, lifegain, knockout.
  - `FX.RIG_ELSE` (stand-ins): wipe→death, player→damage, counter_minus→counter.
  - `FX.RIG_LEN`: the effect lengths. `FX.RIG_AT`: knockout 0.6 s.
- **Effects that play only on a rig** (`rigOnly`, no slot look): exile, countered, lifegain.
- **Status**: the bundle and its link are deployed in main `61e94b6` (memory `mtg-pending-deploy`), **not yet seen live**. The **two-client test** (`docs/m5-assetbundle-build.md` §8) **has never been run**. Whether a host-fired trigger effect shows on another player's screen is still unverified.
- **Test hook**: `engineFxTest("death"|"wipe"|"exile"|..., cardId or colour)` plays one effect on a rig at once. The fake TTS (`tests/lua/tts-sim.lua` ~307) records `AssetBundle.getTriggerEffects`, `playTriggerEffect` and `playLoopingEffect`. The gate is `tests/test_table_effects.js`.

### 1.4 Events the table already detects (`engineEffects` → `engineFxBoard`, 2451 / 2145)

All of these come from comparing **two consecutive boards** (the `FX.prev` snapshot against `now`):

| Event | How it is detected | Spot used |
|---|---|---|
| death | the id is in the last board's battlefield, not in any battlefield now, and is **in a graveyard now**, or was a token (`tok`) that isn't in `exd` / exile | the card's last planned spot `prev.bf[id].pos` (a grouped token uses its group's spot) |
| wipe | **more than 3** deaths on **one seat's** battlefield: one `death_wipe` at the middle of them, "×N". The wipe *sound* is ≥3 deaths over all seats | the centroid of that seat's dead cards |
| exile | the id left the battlefield and is in an exile zone now, **or** is in the bridge's `exd` | the last spot |
| damage to a creature | the card is on the battlefield in both boards and `dmg` rose | the card's spot; delayed to `engineLungeHits[id]` when it was a combat hit |
| damage to a player | `life` went down (life paid reads the same) | `enginePlayerSpot(colour)` (the back centre of their board), delayed to the lunge hit |
| knock-out, counter, lifegain, countered, instant / sorcery cast | (as in the design doc) | |

Caps: 6 effects per board, at most 4 damage bursts and 4 rings. Deaths are staggered by 0.08 s. Jumps (rewind, resend, `started`) play nothing. One sound per board, by priority (`docs/sounds.md`).

## 2. What the bridge sends the table, per board (`sendTable`, `bridge/bridge.js` 4214)

- **Every board**:
  - `turn`, `step`, `active`, `priority`, `gameOver`, `winner`;
  - `players[]` with `life`, `status`, `handCount`, and the zones `battlefield` / `graveyard` / `exile` / `command` (unchanged zones are left out and named in `keep`);
  - `stack[]`;
  - `cards` (the static details, once per card);
  - `rewind`.
- **Per battlefield card** (`tableCard`): `tap`, `p`/`t`, `ctr` (counters), **`dmg`** (marked damage), `att`, `tok`, `ctl`, **`atk`** and **`atkT`** (attack target: a colour or a planeswalker / battle id), **`blk`** and **`blkOf`** (the attackers it blocks), `ew` (exiled with), `cp`, `po`, …
  - The static part is sent once: `n`, `f`, `b`, `tl`, `cmc`, `ty`, `tok`, `bp`, `bt`.
  - **No colour and no mana cost**. `tableCard` doesn't forward `CardDto.color` / `manaCost`, though the engine sends both: `CardDto { color: String, mana_cost: String }` in `manabrew-protocol/src/game/mod.rs:364`, and the bridge reads `c.color` as WUBRG letters elsewhere (lines 1669 and 4758).
- **Per stack item**:
  - `id`, `n`, `tx`, `ctl`, `src` (the source card id), `spell`, `ins`, `sor`, `sp`, `f`;
  - **`tg`**: its targets, `{k:"p", c:colour}` / `{k:"c", id}` / `{k:"s", id}`, from Forge's `TargetChoices` (`InteractiveSnapshotExtractor.stackTargets`);
  - **no colour**.
- **Effect side-channels**: outside the signature, cleared once sent.
  - `jump`;
  - `exd`: card ids moved battlefield → exile since the last board, from Forge's event feed;
  - `ctrd`: the cards of spells countered.
- **The engine's event feed** (`GameViewDto.events`, `EngineEventLog.java`, a ring of 256):
  - It holds **zone moves only**: `{seq, cardId, from, to, ownerId, how, cause, causeName, causeCardId}`.
  - `how`: `sacrificed` / `destroyed` (battlefield departures), `draw`, `discard`, `mill`, `surveil`, `played`, `foretell` / `plot` / `suspend`.
  - `cause`: the resolving ability's ApiType (e.g. `DestroyAll`, `ChangeZoneAll`), or `Cost:<x>` while a cost is being paid, or a replacement's log message.
  - `causeCardId` / `causeName`: that ability's host card.
  - **No `cause` for state-based deaths** (lethal damage, toughness 0). The move happens outside the resolution, and `damageNews` relies on that ("no other cause").
  - The bridge uses the feed for the log and `exd`, and **forwards nothing else** to the table.
- **Damage**: "Forge sends no damage event: GameViewDto.events moves cards only" (`bridge.js` 2595).
  - `damageNews` infers source → target **for the log only**, and only where it is certain:
    - combat: unblocked attackers at the player they attack;
    - one undivided "X deals N damage" item at its targets;
    - "each opponent" / "each player";
    - "each creature" (plain words only).
  - It returns `{lines, loss, gain}`, which become text. **No structured data goes to the table.**
  - **But Forge does fire** `GameEventCardDamaged(card, source, amount, type)` and `GameEventPlayerDamaged(target, source, amount, combat, infect)` (`forge/forge-game/.../event/`). `EngineEventLog` just doesn't subscribe to them.

### 2.1 The four questions

| Question | Can the table know it today? | Detail |
|---|---|---|
| **(a) Source and target of damage** | **Partly.** | **Combat: yes.** The lunge knows each attacker → its blocker or `atkT`, and stamps `engineLungeHits[target] = hit time` (1663-1707). Blocked attackers get their own id too. **Spells and abilities seen on a board: inferable.** A last-board stack item with `tg` that is gone now, while its target's `dmg` rose, `life` fell or it died. Its origin is `engineFxStackSpot[st.id]`: the *last* board's stack spot is still there when `engineEffects` runs, since effects run before the stack layout at 2742 vs 2750. For an ability, its source card is `st.src`. **But**: no amount per item (only the combined dmg / life change); divided damage and two sources at one target are ambiguous; a spell cast and resolved between two boards (an AI's, with nobody stopping) was never on a board, so it has no source; "each opponent" / untargeted pings have no `tg`. The bridge's `damageNews` has better rules but sends only text. |
| **(b) Colours of the spell that caused a wipe** | **No.** | No colour reaches the table, neither on cards nor on stack items. Nor does the cause: `exd`/`ctrd` are the only feed facts it gets. The bridge *has* both. For destroy, sacrifice and exile wipes (`DestroyAll`, `SacrificeAll`, `ChangeZoneAll` …), each move's `causeCardId` → that card's `CardDto.color`. For **damage and −X/−X wipes** (Pyroclasm, Blasphemous Act, Toxic Deluge, Massacre Wurm), the deaths are state-based **with no cause**. The colour has to come from the spell or ability that resolved just before them, from `facts.offStack` (spells only, Forge's order) or from the last board's stack item that is now gone (abilities too). |
| **(c) Died vs exiled vs bounced, per card** | **Mostly.** | Died = in a graveyard now. Exiled = in exile now or in `exd`, so tokens are covered. A non-token bounced, tucked or blinked into a hidden zone = in no public zone, so the table plays nothing (correct). **Gaps**: a **token bounced** to a hand reads as a death (a known limit); "destroyed" vs "sacrificed" vs "dies" isn't sent; a commander moved to the command zone shows nothing. The feed has all of it (`from`/`to`/`how` per card); only `exd` is forwarded. |
| **(d) Timing within one board update** | **No**, apart from combat. | A board is a snapshot: everything between two boards lands at once. The table's only clock inside a board is the combat lunge (`engineLungeHits`), which delays damage and death bursts to the swing. The bridge knows Forge's order (`seq`, `facts.firstSeq`, `offStack`), but it isn't sent. A creature killed by a bolt shows only its death today: its `dmg` rise is never seen, because it left the battlefield in the same board. |

### 2.2 How many died in one board update

The table knows this exactly: `diedIds[colour] = {ids}` per graveyard owner, and `engineFxLast.died`. The counts feed the wipe rule (more than 3 per seat for the cloud, 3 or more in total for the sound) and the sound bursts.

## 3. TTS constraints that matter

| Constraint | Source | Consequence |
|---|---|---|
| A trigger effect plays **once** for its `Duration` (default 1 s). A looping effect plays continuously; one at a time per object, switched with `playLoopingEffect` | `TTSAssetBundleEffects.cs`, TTS AssetBundle API | One-shots for everything. A looping effect could carry a moving trail, but switching it back to `idle` is one more call, and it is the object's persistent state, which goes into the save |
| **No parameters** to an effect (colour, size, target) | AssetBundle API | Colour has to be **baked per effect**, or applied from outside the effect (see the tint probe in 4.2). Distance and direction come from the rig's **transform**: position, rotation, scale |
| An AssetBundle object can be moved by Lua: `setPosition`, `setPositionSmooth`, `setRotation`, `setScale`. Locked objects move fine (rigs do, and so do the lunge's cards) | today's rig code, the lunge | A projectile is either Lua moving a rig, or a baked animation inside a rig that Lua has placed, aimed and scaled once (4.4) |
| Moving per frame (`Wait.frames` + `setPosition`) | – | Each move is host Lua plus a network transform update; clients interpolate, so 18 frames of movement look steppy for them. `setPositionSmooth`'s speed can't be set (TTS's own smoothing) |
| **`destruct()` costs about 360 ms** in the next frame, under the table or not | memory `tts-perf-facts` | **Never spawn or destroy per event.** Keep a pool, made once and kept in the save (today's design) |
| A full TTS session is at ~69k Unity objects plus ~11k for the first game. The GPU TDR crash comes at ~78-84k | memory `tts-live-spawn-crash` | Rigs count. My **estimate** (not measured): today's prefab is about 37 GameObjects with ~25 particle systems, about 100-120 Unity objects per rig, so 6 rigs ≈ 700. Adding 7 wipe colours and a bolt to the same prefab takes it to ~200 per rig; **12 such rigs ≈ 2.4k (~3% of the headroom)**. Textures and materials are shared once per bundle file. Measure with Player.log "Loaded Objects" before and after |
| A rig's spawn data needs `Transform`; the spawn is one-time only, and only at zero rigs | `FX.spawnBundle` / `findRigs` | Growing the pool (more rigs, or a bolt-only rig type) needs a top-up: spawn the missing ones. With a second bundle, also a second GM-notes tag |
| **Multiplayer**: Lua runs on the host only. Transforms replicate. Whether `playTriggerEffect` fired by the host's Lua shows on clients is **not verified** (two-client test unrun). `setInvisibleTo` hiding particles is also unverified | `docs/m5-assetbundle-build.md` §8 | **A blocker for all four effects.** Run check 1 (a trigger shows for the other player) and check 2 (at the right spot, `RIG_LEAD` big enough) first. If triggers don't replicate, rig effects are host-only, and only Object UI slots / highlights / MusicPlayer are shared |
| Ordering on clients: move first, trigger ≥0.1 s later | `RIG_LEAD` | For a bolt: aim and scale the rig, then trigger 0.1 s or more later; the same pattern |
| A late joiner, or a client still loading the bundle | check 7 | Sees nothing for effects fired meanwhile; harmless |
| Built-in `Particles/Standard Unlit` only; one Windows build serves everyone | KB, build doc §5 | Keep to it for every new material |
| Budget: under 5 ms Lua per board on the host | M5 rule | Rig plays are a handful of calls; a per-frame mover would not be |

## 4. Recommendations

### 4.0 Before anything new: verify what is shipped (about 0.5 day; needs TTS and, for 2, a second client)

1. **On the real table**, `engineFxTest("death", <card>)`, then `"wipe"` and `"exile"`.
   - Check that the rigs spawn, the effects show at the card, and the shape and colours read right.
   - Tune `RIG_LIFT`, `RIG_LEAD`, `RIG_TAIL` and the sizes. Screenshot with `tools/tts-shot.ps1`.
2. **The two-client test**, checks 1, 2, 4 and 7 of build doc §8. Every effect below assumes check 1 passes.
3. Measure the Loaded Objects delta of the 6 rigs, to calibrate the pool estimate above.

### 4.1 Death: exists; extend it (about 0.5 day)

- **Keep** the `death` trigger effect and the current trigger: a battlefield → graveyard move, plus tokens.
- **Changes**:
  - **Sequence it after a bolt**. When the dead card was the target of a bolt played on the same board (4.4), delay its death to the bolt's impact time. Write the impact into the same `hits` table the lunge fills (`engineLungeHits[id] = impactAt`), so `FX.dispatch` delays the smoke without new plumbing.
  - Optional: a short `death_hit` variant (a white flash first) for deaths caused by damage. This needs (d)-level data (4.5): whether the death was from damage.
- **Optional bridge field**: `lv` (4.5) would fix the bounced-token-reads-as-death limit.

### 4.2 Board wipe, coloured: new data + baked colour variants (about 1.5-2 days)

**The look**: today's `death_wipe` (one cloud per seat with more than 3 deaths, at their centroid), coloured by the cause.
- Mono W/U/B/R/G: Arena-ish white-gold, blue, black-purple, red-orange, green.
- **C** (colourless, e.g. Oblivion Stone): grey-silver.
- **M** (multicolour): gold.
- Optional: play two mono variants on two rigs for a two-colour spell. The rigs are cheap, but it uses two of the pool.

**How to colour**: one prefab per colour, or parameters?
- **Recommended: bake the variants in the same prefab.** In `MtgFxBuild.cs`, loop over a palette: `death_wipe_W`, `_U`, `_B`, `_R`, `_G`, `_C`, `_M`. That's 7 effects of 3 systems each, and they share the materials and textures. It costs about 20 lines of C#, about 21 more particle systems per rig, and a few KB. It is certain to work, because it needs nothing TTS doesn't already do.
- **Worth a 15-minute probe first: runtime tint.** Does `rig.setColorTint(c)` on a `Custom_Assetbundle` reach the `_Color` of its **ParticleSystemRenderer** materials? `Particles/Standard Unlit` multiplies `_Color` with the particle colour, and tint is an object property that replicates.
  - If it works: one white/neutral `wipe` effect serves every colour, and the bolt can be tinted by its source's colour too.
  - If it doesn't, bake. Either way, the TTS docs don't say whether tint reaches an AssetBundle's particle materials.
- **Avoid: the Component API.** That is `getComponentInChildren("ParticleSystem").set("startColor", …)`. Unknown type support, the obsolete `startColor` property, and probably not replicated to clients.

**Lua**:
- `FX.rigKind` returns `wipe`, plus the colour key.
- `FX.rigName` tries `death_wipe_<key>`, then `death_wipe`, then `death`, through the existing `RIG_ELSE` fallback.
- Optional: lower the visual wipe rule from "more than 3 on one seat" to "the board's wipe cause killed 2 or more", once the cause is known.

**Data the bridge must add** (none of it is on the table today):
- `cl` on the static card (colour letters from `CardDto.color`, sent once per card; a few bytes) and on stack items (the spell's / the source's colour).
- **The cause of each battlefield departure** (`lv`, 4.5): `by` = `causeCardId` from the feed.
  - For a state-based death with no cause, the bridge attributes it to the last spell or ability that resolved before it, in Forge's order. These are `facts.offStack` for spells, plus the last board's stack items that are now gone, for abilities.
  - Or the table does that fallback itself, from `prev.stack` and `cl`.
- Wipe colour = the `cl` of the most common `by` among that board's deaths.

**The exile wipe** (Farewell, Merciless Eviction) can reuse the same palette as `exile_wipe_<key>`, if wanted. A bounce wipe: no effect (Arena shows none).

### 4.3 Exile: exists; small additions (about 0.25-0.5 day)

- **Keep** the `exile` trigger effect: a gold / pale-blue spiral and rising motes. Today it is rig-only, so it shows nothing without the bundle.
- **The trigger is already correct for tokens**, through `exd`.
- If the probe in 4.2 shows tint works, an exile tinted by the source's colour costs nothing extra.
- Optional: `exile_wipe` for 4+ exiled at once (Farewell), the same as the death wipe.

### 4.4 Damage bolt: new effect, new data (about 3-4 days)

**Recommended build: a baked animation, aimed and scaled once by Lua.** That means one trigger effect and no per-frame Lua.

- **In Unity**: a new trigger effect `bolt`. Its child `head` (an `Animation` component with a legacy clip, named in `TTSAnimation.AnimationName`) moves from local (0,0,0) to (0,0,1) over ~0.3 s, with a y-curve for an arc.
  - `head` carries a small glow and a trail emitter (`rateOverDistance`, **World** simulation space, so the trail stays behind).
  - An `impact` child at (0,0,1) bursts at T (start delay).
  - Particle systems use **ScalingMode Shape** (or Local), so particle *sizes* don't grow with the rig's scale while the *path* does.
  - This can be checked in the Unity editor in play mode, with no TTS: scale the parent to 5 and to 30, and the trail and impact must look the same size.
- **In Lua**:
  - the rig goes to the **source** spot;
  - `setRotation` to face the target, yaw plus pitch: the stack floats at y+2.5;
  - `setScale(distance)`, uniform, so the arc scales with the throw (Arena's comet arcs);
  - `playTriggerEffect("bolt")` ≥ `RIG_LEAD` later;
  - set `hits[target] = now + lead + T`, so the existing damage, `player_hit` and death bursts land on impact;
  - reset the scale and rotation at park, or on the next use.
- **Its origin**:
  - a spell: its spot on the *last* board's stack (`engineFxStackSpot[st.id]`), where its target line started;
  - an ability: its source card (`cardSpot(st.src)`);
  - combat: no bolt, the lunge already shows it.
- **Its target**: a card's `prev.bf[id].pos` (it may have died), or `enginePlayerSpot(colour)` (where attack lines end).
- **Colour**: orange-red default. Optional per-source colour variants (`bolt_R` …) the same way as the wipe, or by tint.
- **Pool**: several bolts can share a board (Arc Lightning, Niv-Mizzet pings, Electrolyze). Raise `FX.RIGS` to about 10-12, with a top-up spawn (3), or a separate small `mtg-bolt.unity3d` rig type (fewer Unity objects per rig, if the count matters). Cap at about 4 bolts a board and drop the rest, as the slots do.
- **The alternative**: Lua-moved rigs (`setPositionSmooth`, or a per-frame `setPosition` over ~18 frames, while a trail effect plays). It works without Animation, but its speed can't be controlled, it is steppier for clients and costs per-frame Lua. Keep it as a fallback if Animation clips in a bundle turn out not to play in TTS (check that in the first test).

**The data it needs: source → target → amount, certain, in order.** In rising order of quality:
1. **Table-only, no bridge change** (weak): take the last board's stack items with `tg` that are gone now, and pair them with targets whose `dmg` rose, `life` fell, or that died.
   - Amount: the rise, unless two items hit one target.
   - It misses untargeted pings, items never seen on a board, and divided damage. It can also play a bolt for a non-damage targeted spell, because the "life fell or died" test is fuzzy: a Murder whose target died would fire a bolt.
   - So it also needs the item's text to say "deals … damage" (the table has `tx`).
2. **The bridge sends `hits`** from `damageNews`, which already computes the certain cases: `[{src, to, n}]`, with `to` a card id or a colour, and `src` a stack item or card id. That's about 0.5-1 day, in the bridge only. It shares `damageNews`' blind spots: items never seen on a board, and a bare loss when a source is unknown.
3. **Root cause (best)**: the harness emits damage events.
   - `EngineEventLog` subscribes to `GameEventCardDamaged` / `GameEventPlayerDamaged` (source, target, amount, combat flag, in Forge's `seq` order, alongside the moves).
   - That needs:
     - a protocol change: `EngineEventDto` has `to: String` required and no amount or target fields, so add optional `kind`, `amount`, `targetId`, `sourceId`, `combat`, then `yarn gen:types`;

     - rebuilt engine and relay images (memory `mtg-own-engine-images`);
     - the bridge forwarding `hits` from the feed.
   - That is about 1-1.5 days on top of the bridge work. It is exact for every source (AI spells resolved between boards included), and it gives (d): Forge's order of damage vs death.
   - Commit locally on the `tts-engine` branch, no upstream PR (memory `manabrew-no-upstream-pr`). The ring is 256 entries, shared: a big Pyroclasm adds one entry per creature.

### 4.5 Proposed bridge fields (one change, serves 4.1-4.4)

All of these go outside the board signature and are cleared once sent, like `exd` / `ctrd`:

```jsonc
// static card (once): colour letters
"cards": { "engine-card-40": { "n": "Wrath of God", ..., "cl": "W" } }
// stack item: the spell's colour (an ability: its source's)
"stack": [ { "id": "...", "src": "engine-card-40", "tg": [...], "cl": "W" } ]
// every battlefield departure since the last board, in Forge's order (replaces exd; folds in how and cause)
"lv": [ { "id": "engine-card-12", "to": "g|e|h|l|c|x", "how": "d|s|", "by": "engine-card-40", "q": 1 } ]
// damage since the last board, in Forge's order (option 2: from damageNews; option 3: from the feed)
"hits": [ { "src": "engine-card-40", "to": "engine-card-12" , "n": 3, "q": 2 }, { "src": "...", "to": "Red", "n": 2, "q": 3 } ]
```

- `q` (the order inside the board) lets the table stagger bolt → impact → death in Forge's order, instead of all at once. That answers (d).
- The `to` codes: `g` graveyard, `e` exile, `h` hand, `l` library, `c` command, `x` a token that ceased to exist.

The gates to update are `test_bridge_golden`, `test_bridge_events` and `test_state_delta`. The goldens gain the new fields only on boards with such moves.
